Roadstr — Adaptive UI Rendering Engine

Engineering Specification / Roadmap Prompt for Claude Code

You are working on Roadstr.

For this first pass, DO NOT implement the whole feature. Inspect the
repository and produce a technically grounded architecture, roadmap, and
atomic backlog for an Adaptive UI Rendering Engine. The roadmap must be
structured so work can later be divided between Claude Code and ChatGPT
Codex with minimal overlap.

Do not redesign Roadstr from scratch. Preserve working architecture and
behavior wherever reasonable.

PRODUCT GOAL

Roadstr needs a UI orchestration layer for its navigation experience.
This is NOT a custom geographic/cartographic renderer and must not
replace Flutter’s renderer or the existing map engine.

The Adaptive UI Rendering Engine should dynamically decide: - what UI is
visible; - where it is positioned; - its prominence; - navigation-camera
behavior; - controls shown/hidden; - transitions; - how touch
interaction changes the navigation experience; - how the interface
adapts to navigation state and user intent.

Conceptually:

Navigation state + map state + user interaction + route state + movement
state → Adaptive UI Engine → UI composition + camera intent → existing
Flutter/map stack

The engine should make Roadstr context-aware rather than merely
responsive.

KEY EXPERIENCE

While actively driving: - use a navigation-oriented tilted perspective
where supported; - position the vehicle appropriately for forward
visibility; - follow heading; - emphasize maneuver instructions; -
minimize secondary controls; - optimize information for glanceability.

When the user touches, drags, rotates or pans the map: - temporarily
disengage automatic camera following; - enter an explicit exploration
state; - optionally transition toward a more useful exploration
perspective; - expose appropriate map controls; - reprioritize/collapse
UI without hiding critical navigation information.

After inactivity or an explicit recenter action: - smoothly resume
navigation follow; - restore navigation camera policy; - restore
driving-oriented UI.

Do NOT implement this as unrelated booleans scattered through widgets.

DO NOT BUILD A CARTOGRAPHIC ENGINE

Use the existing map SDK for pitch/tilt, bearing, zoom, center, padding,
camera animation, gestures, layer visibility and styling whenever
supported.

The new layer should issue semantic camera intentions, conceptually
like: - followNavigation - explore - routeOverview - recenter -
resumeFollow

Do not scatter raw map-controller commands across widgets. Establish
clear camera ownership.

STATE-DRIVEN DESIGN

Separate WHAT the UI should do from HOW Flutter renders it.

Conceptually:

RawApplicationState → AdaptiveUiStateResolver → AdaptiveUiState →
Flutter widgets

Investigate useful inputs including navigation status, maneuver state,
route state, speed/movement, heading, GPS accuracy, zoom/pitch/bearing,
map readiness, gestures, recenter requests, orientation, screen size and
safe areas.

Do not add speculative inputs without a real use case.

Investigate explicit high-level modes such as: - browsing -
navigationFollow - navigationExplore - navigationOverview - rerouting -
approachingManeuver - stopped - arrived

Use repository-appropriate naming. Avoid combinatorial boolean state.

CAMERA ORCHESTRATION

Design a dedicated semantic camera layer responsible for: - following
user/heading; - route overview; - exploration camera; - recenter; -
pitch/bearing transitions; - zoom policy; - camera padding based on
UI; - animation timing/easing; - suppressing automatic camera updates
during deliberate interaction.

Screens/widgets must not fight over camera ownership.

TOUCH/GESTURE POLICY

Explicitly model: navigationFollow → user pans → navigationExplore.

During exploration, automatic follow must not fight the user.

When interaction ends, begin a configurable inactivity policy rather
than snapping back immediately.

Explicit recenter should immediately request navigation-follow mode.

Automatic resume may occur after a configurable timeout. Keep timeout
policy centralized and testable.

ADAPTIVE UI COMPOSITION

Resolve presentation centrally. Consider typed values for: -
primary/secondary maneuver presentation; - speed and ETA visibility; -
map controls; - recenter; - route overview; - compass; - bottom panel
mode; - instruction panel mode; - map viewport insets/padding; - camera
mode.

Prefer richer enums/sealed models over dozens of booleans.

Driving mode must prioritize maneuver, maneuver distance, road name,
route, speed, ETA/distance, then secondary controls.

CAMERA + UI COORDINATION

Camera framing must understand occupied UI space. If panels change size,
derive map viewport padding from the same resolved UI state. Do not
hardcode map-center offsets independently from layout.

Design a shared concept such as MapViewportInsets / UiOcclusion /
CameraPadding according to repository conventions.

POLICY VS MECHANISM

Separate behavior policy from map/Flutter mechanisms.

Example policy: When navigating and the user pans, enter exploration
mode and resume follow after inactivity.

Mechanism: Invoke the existing map SDK camera API.

Most behavior policy should be unit-testable without rendering a map.

CONFIGURATION

Centralize tunables: - exploration timeout; - animation durations; -
pitch values; - navigation zoom ranges; - stopped-state delay; - control
visibility timeout; - any justified thresholds.

No scattered magic numbers.

PERFORMANCE

Avoid rebuilding the entire navigation screen for every GPS update.
Isolate selectors/listeners, throttle/debounce only where semantically
safe, avoid needless allocations and repeated controller creation, and
document high-frequency paths.

Do not throttle safety-critical maneuver information for cosmetic
performance.

TESTING

The policy/state engine should be strongly unit-tested.

Required scenarios should include: - navigation follow + pan →
exploration; - exploration + timeout → follow request; - exploration +
recenter → immediate follow; - follow + route overview → overview; -
navigation ends → browsing; - rapid/competing transitions; - GPS/heading
unavailable; - map controller not ready; - interrupted camera
animations; - app lifecycle changes.

Abstract/mock camera SDK calls where practical.

MIGRATION

Do not rewrite the navigation screen in one giant commit.

Prefer an incremental migration: 1. characterize current behavior with
tests; 2. introduce state models; 3. introduce camera abstraction; 4.
route existing camera commands through it; 5. introduce interaction
state; 6. introduce adaptive composition; 7. migrate widgets
incrementally; 8. remove obsolete logic; 9. profile/polish.

Keep the app buildable at major checkpoints.

DO NOT OVER-ENGINEER

This engine exists specifically for Roadstr. Do NOT build: - a generic
plugin framework; - a replacement Flutter rendering tree; - a custom
layout engine where Flutter suffices; - reflection/DSL infrastructure; -
an event bus just because the word “engine” sounds architectural; -
unnecessary service locators.

The engine should mainly provide: state resolution + policy +
orchestration + camera coordination.

Flutter remains responsible for widget rendering.

SUCCESS SCENARIO

The final architecture should cleanly support:

1.  Navigation starts.
2.  Roadstr enters navigation-follow.
3.  Camera uses navigation pitch/bearing/zoom.
4.  UI prioritizes maneuver information.
5.  User drags the map.
6.  Engine detects exploration intent.
7.  Follow pauses.
8.  Camera transitions appropriately.
9.  Exploration controls appear.
10. Navigation information remains available but reprioritized.
11. User stops touching.
12. Inactivity policy begins.
13. Roadstr does not fight continued exploration.
14. User taps recenter OR timeout expires.
15. Camera smoothly resumes navigation.
16. Driving-oriented UI returns.

This must be driven by explicit, testable state rather than widget-local
hacks.
