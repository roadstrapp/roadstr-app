# World discovery — decision log

Decisions taken while planning and building, each with the reason and what
would reverse it. They follow the rules the project already works by: privacy
first, nothing Google, nothing mandatory, nothing hidden, and the navigation
core never depends on the discovery layer. Newest entries at the bottom.

| ID | Decision | Why | Reverse if |
|---|---|---|---|
| D-01 | Plan and implement on the Kotlin road-test root now, even though the migration gate in the original brief (R-01…R-05, R-17) is still open. Nothing changes in the Flutter app or the `app.roadstr` package. | The work is additive and Kotlin-only; waiting would only move it. The gate protects the production update path, which this does not touch. | The cutover plan requires the feature set to be frozen. |
| D-02 | Do not edit fixture-locked protocol files. New behaviour lives in new files; a locked file may only gain an additive native-only field with a default. | They are byte-for-byte mirrors with Dart oracles; a silent change breaks parity tests. | Flutter is retired and the oracles are deleted. |
| D-03 | Per-locale lexicons are TSV text in Kotlin raw strings, not Android assets. | Same data in both Gradle roots and in JVM tests, no I/O, no asset plumbing, reviewable as one-file diffs. | Lexicons grow beyond a few hundred lines each. |
| D-04 | Write a Unicode-aware normaliser instead of reusing `FuzzyMatch.normalize`. | `FuzzyMatch.normalize` turns every non-Latin letter into a separator, so Greek, Cyrillic, Japanese and Chinese would parse as empty. | `FuzzyMatch` is fixed (its Dart oracle would have to change too). |
| D-05 | Web discovery is **Off** by default, with modes Off / Ask / On. No default instance, no Roadstr-operated server, no suggested public instance list inside the app. | Web search has more exposure than the OSM providers; the user must opt in and choose who receives the text. | — |
| D-06 | Default source policy blocks engines whose name contains `google` and `startpage`; the engine allowlist is built from the instance's `/config` and sent as `engines=`. If `/config` is missing, filter results by `engines` and say so. A strict mode refuses instances without a buildable allowlist. | Matches the "no Google" rule without claiming what Roadstr cannot verify about upstream engines. | The user disables the policy explicitly. |
| D-07 | Web requests carry text only: query, interface language, safe-search level. "Near me" becomes a coarse locality name from a reverse lookup of coordinates rounded to two decimals. Exact coordinates are never sent. | Same rounding already used for Photon bias; the locality is enough for a web query. | A provider genuinely needs coordinates and the user consents per request. |
| D-08 | Every new Nominatim call goes through a shared ≥1.1 s pacer and an in-memory cache; the User-Agent carries the project URL; no autocomplete; no grid or corridor reverse lookups. Endpoints are configurable. | The OSMF policy caps the whole application at 1 req/s, forbids autocomplete and systematic reverse queries, and asks for switchability. | Roadstr runs its own geocoder. |
| D-09 | A place becomes a map pin only when it comes from OSM (it has an OSM id) or its resolution confidence is ≥0.8. 0.5–0.8 is shown as candidates; below is a plain web result. A brand name alone never merges two places. | Never put a misleading pin on the map. | — |
| D-10 | Roadstr never fetches a SearXNG result URL itself. Result pages are only opened in the browser under the navigation policy. | Result URLs are attacker-influenced; fetching them natively would be SSRF with the user's network position. | — |
| D-11 | GeckoView is an **opt-in build variant** (`-Pgeckoview=true`): minSdk 26, one ABI, `play-services-fido` excluded and stubbed, lazy runtime, no prewarm, idle shutdown. The default build keeps opening the system browser through the same `WebBrowserHost` interface. | The AAR needs minSdk 26 (project is 24), adds ~86 MiB per ABI, and pulls a Google SDK that the project forbids; the F-Droid main repo is unlikely to accept a prebuilt Mozilla binary. | Measurements show the cost is acceptable for every ABI and the F-Droid maintainers accept it. |
| D-12 | Web-discovery queries never enter place-search history; the browser is ephemeral (private sessions, storage cleared on close, no history, no autofill). | Keeps the existing privacy semantics of the history list. | The user asks for browser history; it would be a separate, explicit, clearable store. |
| D-13 | No type-ahead, no background refresh, no prefetching of result pages. Browser permissions (location, camera, microphone, notifications, XR, storage, local network) are denied; popups are denied. | Battery work already done must not regress; a restaurant site must not inherit the app's GPS permission. | A per-site consent dialog is designed and reviewed. |
| D-14 | The query interpreter is rule-based behind `QueryInterpreter`; no cloud model and no model dependency. | Matches the no-central-server rule; leaves room for a local model later. | — |
| D-15 | "Open now" is evaluated only for places within 100 km of the device, using the device clock; farther places show the raw hours and "unknown". Complex rules the evaluator does not understand stay unknown. | The evaluator takes a local time without a zone; a wrong clock would claim a place is open when it is not. | Time-zone resolution per place exists. |
| D-16 | The SearXNG instance URL is stored in the protected (Keystore) preferences, like the routing key; Settings shows only the host. | A self-hosted address says something about the user's network. | — |
| D-17 | No on-device verification in this task (no adb). Device checks are listed in the plan and left to the owner. | Standing rule about adb. | The owner authorises it. |
| D-18 | The feature is Kotlin-only; no Dart mirror. Dart tests are contract tests that read the Kotlin source for guard rails. | Flutter is being retired. | — |
| D-19 | The prompt files stay out of version control; the plan and decisions are committed. | Existing instruction about the prompt files. | — |
| D-20 | The web search choice (mode, instance address, "my own instance", strict sources, safe search) is stored as **one** encrypted value under its own Keystore alias. A missing, damaged or oversized value decodes to Off with no instance. It does not touch the Flutter-compatible settings store. | Whether someone uses web search, and which server they picked, is private; one value cannot be half-written; the closed settings key set stays closed (D-02). | A settings migration moves everything to one encrypted store. |
| D-21 | No separate "coarse location" switch. The mode is the consent; the only position-derived thing a web query can carry is the name of the town, and only for "near me" searches. The question before sending says so ("the name of your town will be added"), and the privacy text lists it. | Fewer knobs, and a disclosure that matches what is sent: the typed words alone would have understated it. | A provider needs more than a town name (then per-request consent, D-07). |
| D-22 | The address box saves when it loses focus as well as on Done, and refuses an address that can never work instead of saving it; plain http to a local network is kept but waits for the "my own instance" box and says so. | Nobody loses a typed address by leaving the screen; the saved value is always either usable or visibly waiting for one tick. | — |
| D-23 | The generator escapes a leading `?` or `@` in Android string values. | aapt reads them as references; the Japanese hint started with `?` and broke resource linking. | — |
| D-24 | Contract test for "never Google" now has two parts: the OSM-only rule for place discovery, and for the web package that Google may be named only where it is blocked, with no built-in address and no coordinates in request code. Comments are ignored when looking for addresses. | The first form was a blunt word search that failed once the blocklist existed; commit bc5364b went out with that test red and this fixes it. | — |
| D-25 | A web result is tied to a place by fixed evidence weights (OSM id 1.0, website 0.85, phone 0.8, street address 0.8, name and area 0.6, proximity 0.1–0.3, category 0.1), combined as `1 − Π(1 − w)` and capped at 0.99 without an OSM id. ≥0.8 links it, 0.5–0.8 offers "could this be…?", below stays a plain web result. | The thresholds are the ones D-09 set; fixed weights keep the outcome explainable and testable. | Real traffic shows the weights link wrongly or never. |
| D-26 | A brand name never links two places. Several branches sharing a name or a website drop to weights that cannot reach the candidate threshold alone, so only a phone number or a street address picks a branch. Listing sites (Facebook, TripAdvisor, Google, …) never match by address, and on site builders (`*.wixsite.com`, …) the whole host is the identity. | Merging the wrong branch or the wrong business is worse than showing a plain result. | A verified chain-store source tells which branch a page is about. |
| D-27 | Name lookups for results the search did not explain: at most 3 per search, the same name once, through the shared Nominatim pacer and a day cache. The query is a name taken from a public page title plus a town, never what the user typed. A looked-up place is accepted only if its name is close, it is inside the search area, and its category or website agrees. It gets a map pin only when linked (≥0.8). | Follows D-08 and D-09; useful without any new network surface. | A provider with a better lookup API replaces it behind `PlaceLookup`. |
| D-28 | The web settings screen says that names from the results may be looked up on OpenStreetMap; there is no separate switch for it. | The lookups only happen after the user asked for web results, and a second switch would be a knob nobody can reason about (same idea as D-21). | The lookups ever send more than a name and a town. |
| D-29 | The GeckoView variant is built with `native-android/gradlew-geckoview`, which has its own Gradle wrapper (9.3.1) and passes `-Pgeckoview=true`. The default wrapper stays at 9.1.0, the default build is byte-identical to before (same APK size, minSdk 24, three ABIs), and every variant change sits in one `if (geckoView)` block of the app build file and in `pluginManagement` of the settings file. | GeckoView 157 pulls androidx.core 1.19 and lifecycle 2.11, which need Android Gradle plugin 9.1.0, compileSdk 37 and so Gradle 9.3.1. Forcing older AndroidX under a library built against the new one cannot be tested without a device; changing the pinned toolchain for everyone was not asked for. | Roadstr moves its whole road-test toolchain to AGP 9.1 and Gradle 9.3.1; the second wrapper then goes away. |
| D-30 | The Gecko runtime is created on the first page opened, never at app start, and is not shut down while the process lives. Memory is given back by closing the session and clearing the engine's storage. This replaces the 120 s idle shutdown of the plan. | `GeckoRuntime.shutdown()` stops the engine thread for good (`GeckoThread.forceQuit`), and creating a runtime again in the same process is not something the library supports; a shutdown would turn the next page into a crash. | A device run shows a runtime can be restarted, or Gecko is moved to its own process. |
| D-31 | Every address the in-app browser is asked to open passes `WebNavigationPolicy`: initial load, link, redirect and new window alike. https loads, http is retried as https, tel/mailto/geo are confirmed by the user and handed to the system by Roadstr (never started by the page), everything else is refused, and the device's own network and local names are always blocked. A window the page tries to open is loaded in place, not in a second session. | One small pure table is easier to audit and test than delegate code, and a search result must not be able to reach the user's router. | — |
| D-32 | The variant excludes `com.google.android.gms`, forces the Kotlin stdlib to the project's 2.2.10, and removes GeckoView's exported clipboard provider. The APK defines no `com.google.android.gms` class; four references to `gms.fido` types remain inside `WebAuthnTokenManager`, which never loads because WebAuthn is switched off. The variant adds only `WAKE_LOCK` and `MODIFY_AUDIO_SETTINGS` to the manifest. | The project ships no Play Services code (a test enforces it); the stdlib alignment and the missing fido classes are verified only by running the variant. | A device run shows a crash from either. |
| D-33 | The Wikipedia reader keeps its existing WebView; only web search results go through `WebBrowserHost`. | Moving it would change what the default build does for a feature that works. | The in-app browser is accepted for every build. |
| D-34 | In the default build web results open in the user's own browser through `SystemBrowserHost`, after the same policy check; plain http is handed over as it is because the browser has its own warning and refusing would leave no way to open a site without https. | Same behaviour as before for good addresses, one place that refuses bad ones. | — |
| D-35 | What a page says about its own place reaches Roadstr through a bundled built-in extension, in the GeckoView variant only: a content script (https pages, top frame, no network, no `eval`, no page access to it) sends one message to the extension's background script, which passes it to the app. The app checks it again against a strict schema (version, https address, at most 8 scripts of 64 KiB, a fixed list of meta tags, 64 KiB in all) and accepts it only if the page's site is the one on screen. | The page is untrusted end to end; a small fixed message and two independent checks leave it nothing to exploit. | A device run shows a simpler path (content script to native directly) works with the same guarantees. |
| D-36 | A page's claims are evidence, not facts. Its coordinates count only inside the search area; with nothing else they make a candidate (confidence ≤ 0.73) and never a map pin; they link to a place of the map only if that place is within 150 m and name, website or phone agree. "Navigate here" from a page always goes through the same confirmation as any map link. | Same thresholds as D-09 and D-25; a page must not be able to move the user's destination, let alone to the other side of the world. | — |
| D-37 | The JSON-LD reader accepts only place-like schema.org types, caps blocks, size, nodes (400), depth (8) and places (8), keeps only https links, checks phone numbers and opening hours against a pattern, treats (0, 0) as unknown, and never evaluates anything. | Page markup is attacker-controlled input. | — |
| D-38 | The extension messaging path is EXPERIMENTAL: that a built-in extension runs in a private session (`setAllowedInPrivateBrowsing`), reaches the app through its background script and delivers a message was not run on a device. If it does not work, pages load exactly the same and no "navigate here" bar appears. | Honest status; the browser never depends on the extension. | A device run proves or breaks it. |
| D-39 | "Along my route" searches the stretch still ahead (30 km), cut at the driver's position on the route, simplified to at most 24 points (Douglas–Peucker, tolerance 10 m growing by half until it fits, the error bound stated) with a 1 km buffer, in one Overpass request per search. Places are ranked by the detour they cost (twice the side step) and show the distance ahead along the route. | One bounded request instead of many; the number a driver wants is how far ahead and how far out of the way. | A routing-based detour is computed for the top results on selection (not done). |
| D-40 | The polyline form of `around` (`around:<buffer>,lat,lon,lat,lon,…`) was checked on a live mirror on 2026-10-05: `z.overpass-api.de` answered with places along a three-point test line; the other two mirrors were overloaded at that moment and answered with a timeout, not a syntax error. | It was the one unverified piece of the corridor query. | — |
| D-41 | Without a usable route (none, too short, or the driver more than 3 km from it) "along my route" keeps the earlier behaviour: the search runs around the user and a notice says the route was not used. No caching by progress bucket: the search runs only when the user asks, so a moved start point simply makes a new request. | Never fail, never invent a route. | Real use shows repeated searches along one route are common. |
| D-42 | Text that comes from the web or from map tags loses the characters that can scramble or disguise a line on screen: DEL, the C1 controls, the zero width space, the word joiner, the byte order mark, and the bidirectional embeddings, overrides and isolates. The zero width joiners and the left-to-right and right-to-left marks stay. | U+202E can make a result read backwards; scripts such as Persian need the joiners. | A script is found to need one of the removed characters. |
| D-43 | The in-app browser's state changes live in a pure reducer, tested without an engine. When the engine dies the browser stays open on the same address with a note, and reload starts a new session. | A crash must leave the app standing and offer a retry; the first version closed the session and could not reload it. | — |
| D-44 | `native-android/verify-geckoview-variant.sh` is the check that both builds stay what they are claimed to be (package, minSdk, ABIs, no exported clipboard provider, no Google Play Services class, no sensitive permission, GeckoView and the page extension only in the variant). | A claim about an APK is only worth what builds and inspects the APK. | A CI job runs the same checks. |
| D-45 | The README and the localisation review say that only seven languages have a full search vocabulary and that no language has had a native review. | The first README draft said "27 languages"; the lexicon sizes say otherwise, and a contract test now keeps the statement tied to the files. | Native reviewers extend the core vocabularies. |
| D-46 | The two native libraries that are not 16 KB aligned (`libespeak-ng.so`, `libroadstr_voice_jni.so`) are a task, not a decision to live with: relink ours with `-Wl,-z,max-page-size=16384` (the CMake file sets no linker flag; NDK 27 does not default to it) and rebuild eSpeak NG through `tools/build_espeak_android.sh` with the same flag, updating the pinned checksum. The Flutter production app already ships the eSpeak NG problem, so this is not a regression of the Kotlin build. **Done 2026-10-06:** `libroadstr_voice_jni.so` is linked with the flag, and the three `libespeak-ng.so` were rebuilt from the same pinned sources with the flag (the data archive keeps its hash, and a second run reproduced every hash); a release APK now shows `p_align` 0x4000 on all of its libraries on arm64-v8a and x86_64, checked with the same script as in MEASUREMENTS.md. | Measured on a Pixel 10 with Android 17 (MEASUREMENTS.md, section 3): the system warns at every start of a debug build, and 16 KB pages are becoming the default. | A different phonemizer replaces eSpeak NG. |
| D-47 | The engine contacts `content-signature-2.cdn.mozilla.net` on its own, even for a page that loads nothing else. It is recorded as a known contact, not hidden by the privacy text of the browser. Options, none chosen: accept it (it serves certificate chains for signed engine data, no page content), cut the engine's remote settings with preferences (this also stops tracking-list and revocation updates), or route nothing until the user opens a page (already true). | A measured fact against a claim that must stay true: the browser sends nothing the user did not ask for. | The owner decides after a real packet capture. |
| D-48 | The in-app browser stays opt-in, and the cost is stated: about +0.9 to +1.1 GiB of memory with any page open, 0.66–0.74 GiB of it kept after closing, and about 1.5 cores for a page like Wikipedia's mobile site. Ideas not done: run the browser screen in its own Android process so that closing it frees the whole engine, and stop the crash-helper process. | D-30 (the runtime is never shut down) has a price that the device shows; a separate process would remove it at the cost of a second activity and process boundary. | The owner picks the process split. |
| D-49 | The update-path candidate build (`-Pcandidate=true` in `native-android`) is kept in the repository: `app.roadstr`, code 2051, signed with the release key read from `android/key.properties` at build time (never stored). The safe way to run it on a real phone is to prepare a Flutter build with a higher code first (2052 here), because Android cannot go back to a lower code without uninstalling. | The test of 2026-10-05 proved the update path both ways on a real phone; repeating it with the migration wired needs the same recipe. | The migration work replaces it with a release script. |
| D-50 | Web results stay an advanced feature that is off by default: the user types the address of a SearXNG instance, normally their own (self-hosted, also one reached over a VPN). Roadstr ships **no default instance and no fallback list**, and never sends the same query to a second server after a failure. The settings text and the connection test say what is wrong with an address (JSON off, rate limit, bot check). Everyone else keeps the place search on OpenStreetMap and the existing "search the web" of the place panel, which opens the engine the user chose in their own browser. Looked at on 2026-10-05/06 and **not taken**: public SearXNG instances (of 81 only 2 accepted the app's requests on the first pass and none passed three rounds), 4get (its official instance wants a captcha pass), Marginalia (the shared public key was exhausted; a personal key is free for non-commercial use on request and the data comes under CC-BY-NC-SA 4.0), YaCy (the one public node reached answered in 24-30 s with no results, and global queries are forwarded to other peers), Tavily (its terms let it retain queries and train on them), and paid search APIs (the key cannot ship in the APK, so they need a server of ours or the user's own key). | Public operators close their instances to API clients on purpose (JSON off, limiter, JavaScript checks), so a built-in default would break for most users, and it would send every user's words and IP to one volunteer's server that never agreed to it. Silent fallbacks would spread one query over several operators. The owner decided this on 2026-10-06. | A server run by the project is ever built (its cost, and the privacy duties of seeing users' queries, are then a decision of their own), or an operator agrees in writing to serve the app. |
| D-51 | The Kotlin app that replaces the Flutter app is the **production module** (`android/app`, same package, same signing key), with the Kotlin launcher chosen at build time (`-Pnative_launcher=true`; Flutter stays the default until the owner approves the switch). The Flutter engine stays in the APK **only** as the temporary reader of the old data, as `MIGRATION_PLAN` already required. The Kotlin app keeps its data in the live stores proven in the road-test app, under their own names (`live`, never `roadtest`), and the road-test APK is untouched. The migration-oriented stores in `storage/` (sealed files with revision fences and digest markers) are not used by the app: they were built for a design whose live side was never finished, they stay in the tree, and removing them is a separate, later cleanup. | The profile has to arrive in the stores the app actually reads, and the road-test stores had been used on a phone while the sealed ones had no secret reader or shell adapter. One import into proven stores is smaller and checkable than finishing a second storage stack. | The sealed stores get their live side and the app moves onto them. |
| D-52 | The import is **fail-closed for what identifies or belongs to the person** (identity, favourites, parking, secrets, queued reports, activity) and **tolerant for the rest**: a bad setting falls back to its default, an unreadable search history starts empty, and keys the new app does not know are left in the old files instead of refusing the update (`TolerantLegacySnapshotReader`; the strict validator still checks everything that is imported). The old files are never written or deleted, a failure leaves the "done" flag unset so the next launch tries again, and the person sees the existing "protected data unavailable" screen, never an empty profile. | A real settings box keeps keys that older versions wrote and later ones stopped using; refusing the whole update over one of them would strand a person on an error screen with no way on. | A key that really matters turns up among the ones left behind. |
| D-53 | The recovery screen after a failed import has **two buttons**: "Try again" (the import starts clean, nothing was written to the old files) and "Continue without importing" (the import is recorded as done and the app starts with an empty profile; the old files stay on the phone untouched and are not read again). Both are the person's choice and neither runs on its own. The screen and its four strings exist in all 27 languages (the two recovery strings used to be English everywhere). | A failure the tests did not foresee must not strand a person on an error screen, and starting empty must never happen unless they ask for it. | A way to import later from Settings is added, so "continue without" is not one-way. |
| D-54 | A release candidate is always prepared **with its way back**: before the Kotlin candidate is installed, a Flutter build from `main` with a higher version code (`2054` against a candidate `2053`) is built and signed with the same key, because Android cannot go back to a lower code. The recipe is `git archive` of `main` into a scratch folder, the literal `versionCode` raised, `android/key.properties` copied in, `flutter build apk --release`. | A signed update cannot be undone by installing an older build; D-49 already learned this on the owner's phone. | Never: the recipe is cheap. |
| D-55 | The Kotlin app logs in **only through Amber (NIP-55) or a remote signer, a "bunker" (NIP-46, a `bunker://` link with at least one `wss://` relay)**. The login with a pasted private key (nsec) is removed, and so is every signer that holds the account's key; the Flutter maintenance branch keeps it. The only key the app keeps for a bunker is its own, which identifies this app to the signer and encrypts the conversation, and it is stored encrypted in the Android Keystore. A private key of an earlier build is erased on the first start, the person is logged out and a notice says why; a Flutter install that was logged in with a private key comes over without that login (the favourites, settings and the rest still import) and gets the same notice. | A private key inside an app can be read by anyone with code on the phone or a memory dump, and the JVM can neither wipe it nor sign in constant time (R-24); with Amber or a bunker the key never reaches this phone. Owner's decision, 2026-10-07: "togliamo il login con nsec e lasciamo solo amber e bunker". | A signer that needs the key inside the app is wanted again, or a bunker flavour that Roadstr cannot talk to (for example `nostrconnect://` only, as Amber offers to other apps) has to be supported. |
| D-56 | **Release 0.6.0 is the Kotlin app.** The owner approved the switch on 2026-10-07: the Kotlin launcher is now the default (`-Pnative_launcher=false` builds the old Flutter one), the version is `0.6.0+2057`, `main` is fast-forwarded to the Kotlin branch, and the Flutter app stays on the branch `flutter-maintenance`, cut from `main` as it was (2608975), so fixes can still ship while the supported window lasts. The Flutter engine stays in the APK only as the reader of the old data (D-51). The update from 0.5.x keeps the profile (D-52) except a private-key login (D-55). Tagging and publishing are separate steps that the owner confirms. | The Kotlin app proved the update on a real phone, drives with the screen off, keeps its data and covers the features the owner uses; the open points that remain are listed in `RISKS.md` with what they need. | A defect that needs the Flutter build back: install the rollback build with a higher code (D-54). |
