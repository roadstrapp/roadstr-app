ROADSTR — OPEN WORLD DISCOVERY + GECKOVIEW + SEARXNG
POST-FLUTTER→KOTLIN FEATURE PROMPT

TARGET REPOSITORY
https://github.com/roadstrapp/roadstr-app

TIMING
Use this prompt ONLY AFTER the Flutter → native Kotlin migration has reached a stable,
feature-parity state and the in-place update/migration path has been proven.

VISION
Roadstr must evolve from:

    "a TomTom-like navigator"

into:

    "an open, privacy-respecting hub from which the user can interact with the world."

The search bar must stop being limited to addresses and known POIs.

Examples of desired user queries:

    "vegano nei dintorni"
    "gluten free a Firenze"
    "bistecche di manzo a Trieste"
    "farmacia aperta vicino a me"
    "parcheggio vicino alla stazione"
    "cinema a Bologna"
    "ristorante siciliano a Ravenna"
    "negozio di elettronica aperto ora"
    "bar con terrazza vicino alla destinazione"

Roadstr should understand the intent, search the best available OPEN/FOSS-compatible
sources, place useful candidates on the map, let the user inspect them, and turn any
resolved place into a normal Roadstr destination/navigation target.

When a place has a website or the user wants richer web information, Roadstr should be
able to open and interact with that content INSIDE Roadstr through Mozilla GeckoView,
rather than depending on Google/Chrome/WebView behavior.

For broader web discovery that cannot be satisfied from OpenStreetMap data alone,
integrate SearXNG as an OPTIONAL provider.

Roadstr's existing FOSS / privacy / no-unnecessary-central-server philosophy remains
non-negotiable.

==============================================================================
2. SEARCH STRATEGY: CHEAP / STRUCTURED FIRST, WEB SECOND
==============================================================================

Use a staged search pipeline.

STAGE A — LOCAL QUERY PARSING

Parse the query into structured intent where possible.

Example:

    "vegano nei dintorni"

becomes conceptually:

    intent = FIND_PLACE
    category = restaurant
    attributes = diet:vegan=yes
    spatialIntent = NEAR_ME

Example:

    "gluten free a Firenze"

becomes:

    intent = FIND_PLACE
    category = restaurant
    attributes = diet:gluten_free=yes
    spatialIntent = IN_PLACE
    placeText = Firenze

Example:

    "parcheggio vicino alla stazione"

becomes:

    intent = FIND_PLACE
    category = parking
    spatialRelation = NEAR_REFERENCE_PLACE
    referenceText = station

Do not use a mandatory cloud LLM merely to parse queries.

Start with deterministic/local parsing:
- normalized text;
- locale-aware synonyms;
- known place categories;
- OSM-tag mappings;
- diet attributes;
- "near me" expressions;
- "open now" expressions;
- "in <city>" expressions;
- "near destination";
- brand/name detection where current search already supports it.

Design the parser so a future OPTIONAL local model/semantic parser can be plugged in,
but do not make that a dependency of this project.

STAGE B — STRUCTURED OPEN DATA

Try the existing Roadstr geographic providers.

Examples:
- address/place/name -> Photon/Nominatim;
- category/brand/OSM attributes -> Overpass;
- current position/location bias -> existing location state;
- "in Firenze" -> resolve geographic area first, then query inside it;
- "near destination" -> use the current route destination as spatial context.

STAGE C — WEB DISCOVERY

Only when:
- structured sources are insufficient;
- the query is clearly about information that OSM typically does not model well;
- or the user explicitly asks for web results;

invoke an optional WebDiscoveryProvider backed by SearXNG.

Example:

    "bistecche di manzo a Trieste"

OSM may know:
    restaurant
    cuisine=steak_house

but it may not know:
    current menu
    specific dishes
    website/menu text

In that case:
1. query structured OSM data first;
2. optionally query SearXNG;
3. resolve web results back to real places;
4. only pin a result after sufficient geographic/entity confidence.

Never put arbitrary search-result URLs on the map as if their location were known.

==============================================================================
5. SEARXNG ROLE
==============================================================================

Integrate SearXNG as an OPTIONAL open-source METASEARCH provider.

Important distinction:

SearXNG itself is open-source.
The upstream engines configured by a SearXNG instance may be proprietary services.

Roadstr must not falsely label every result as "open-source data".

Roadstr's existing "no Google" philosophy must remain explicit.

Therefore design:

Web discovery:
    Off
    Ask when needed
    On

SearXNG instance:
    user-configurable base URL

Optional advanced controls:
    - allowed engines/categories
    - language
    - safe-search setting
    - test instance
    - show instance capabilities

Do not hard-code a dependency on one Roadstr-operated SearXNG server.

Roadstr should continue working if:
- SearXNG is disabled;
- the configured instance is offline;
- JSON output is disabled;
- rate limits occur;
- an upstream engine fails.

NO mandatory Roadstr backend.

==============================================================================
6. SEARXNG API CAPABILITY DETECTION
==============================================================================

Current SearXNG supports `/` and `/search` and can return JSON when the instance enables
the `json` format. Many public instances disable JSON.

Therefore DO NOT assume:

    GET /search?q=...&format=json

always works.

At configuration/test time:

1. normalize/validate base URL;
2. use HTTPS by default;
3. inspect `/config` when available;
4. determine enabled categories/engines;
5. test whether JSON search is enabled;
6. handle 403 for disabled output formats;
7. handle 429/rate-limit behavior;
8. use bounded response sizes;
9. use strict timeouts;
10. never silently switch to a random third-party instance.

If JSON is unavailable:
- either mark the instance incompatible for structured Roadstr discovery;
- or propose a carefully justified alternative.

Do not build a fragile HTML scraper as the default solution.

==============================================================================
7. NO-GOOGLE / SOURCE POLICY
==============================================================================

Roadstr must not silently route its discovery through Google merely because a chosen
SearXNG instance happens to expose a Google engine.

Research how current SearXNG allows engine selection and capability discovery.

Create a source policy abstraction.

Conceptually:

SearchSourcePolicy {
    allowedEngines
    blockedEngines
    allowUnknownEngines
}

Default Roadstr policy should preserve the project's philosophy.

At minimum:
- do not explicitly request Google engines;
- do not call Google APIs directly;
- make SearXNG instance provenance transparent;
- if strict "no Google-backed upstreams" can be guaranteed only with a user-controlled
  SearXNG configuration, explain that clearly in Settings instead of making a false claim.

Do not conflate:
"Roadstr does not directly call Google"
with:
"no upstream SearXNG engine ever talks to Google."

==============================================================================
8. PRIVACY-FIRST WEB DISCOVERY
==============================================================================

Web discovery has more privacy exposure than Photon/Nominatim/Overpass.

Do not automatically append exact GPS coordinates to every SearXNG query.

For:

    "vegano nei dintorni"

Roadstr may know the exact coordinate locally.

Default privacy strategy should be:

1. satisfy it using OSM/Overpass first;
2. if web discovery is needed, derive the minimum useful geographic context;
3. prefer city/neighbourhood/coarse area text over exact latitude/longitude;
4. only send exact coordinates if technically necessary and explicitly justified.

Example:

Instead of:

    vegan restaurant 44.4183591 12.2035298

prefer:

    vegan restaurant Ravenna

when that is sufficient.

Document all data sent to a SearXNG instance.

Add Settings text explaining:
- the selected instance receives search queries;
- enabled upstream engines may receive them from the instance;
- Roadstr itself should not operate hidden telemetry around these searches.

9. WEB RESULT -> REAL PLACE RESOLUTION
==============================================================================

This is a critical subsystem.

A SearXNG result is a WEB RESULT, not automatically a ROADSTR PLACE.

Create a PlaceEntityResolver.

Inputs may include:
- title;
- URL;
- snippet;
- detected business name;
- address;
- locality;
- structured page metadata;
- OSM candidates;
- Photon/Nominatim candidates;
- current search geography.

Output concept:

ResolvedPlaceCandidate {
    place
    confidence
    evidence
    sources
    ambiguity
}

Confidence should be based on explicit evidence:
- exact address match;
- same name + locality;
- phone/domain match if available;
- coordinates from structured metadata;
- OSM ID;
- proximity;
- category agreement.

NEVER invent coordinates.

If confidence is low:
- show the result as a web result;
- allow the user to open it;
- do not drop a misleading pin.

If several real-world places match:
- present candidates for user selection.

==============================================================================
14. GECKOVIEW: WHY IT EXISTS
==============================================================================

GeckoView is NOT the search engine.

GeckoView is Roadstr's embedded open web engine.

Use it for:
- opening a place website;
- reading menu/details;
- following a web discovery result;
- viewing rich public information without leaving Roadstr;
- future safe web-interaction capabilities.

Do not use GeckoView merely to render SearXNG search-result HTML.

Search results should be structured data in Roadstr UI.
GeckoView opens the selected web content.

==============================================================================
28. NETWORK / BATTERY PROTECTION
==============================================================================

Roadstr has already spent significant work reducing battery usage.

This feature must not reintroduce continuous network/CPU churn.

Rules:
- debounce typeahead;
- SearXNG MUST NOT run on every keystroke;
- web discovery should run only on settled query / explicit request;
- cancel obsolete searches;
- single-flight identical requests;
- bound concurrency;
- cache stable results;
- cap HTTP bodies;
- strict deadlines;
- respect 429/Retry-After where available;
- do not background-refresh web searches;
- do not keep Gecko rendering while screen is gone;
- do not prefetch every search result website.

Profile battery/memory after integration.

==============================================================================
29. FAILURE DEGRADATION
==============================================================================

Roadstr must still be useful when the web layer fails.

If:
- SearXNG is offline;
- instance blocks JSON;
- all SearXNG engines fail;
- GeckoView crashes;
- a website refuses to load;
- structured extraction fails;

then:
- OSM/Photon/Nominatim/Overpass search continues;
- routing continues;
- active navigation is NEVER interrupted;
- Roadstr does not crash;
- user gets a concise error/fallback.

The new feature is additive, not a new single point of failure.

37. ARCHITECTURE BOUNDARIES
==============================================================================

Keep these concepts separate:

QueryUnderstanding
    understands what the user asked.

PlaceSearchProvider
    returns structured geographic places.

WebDiscoveryProvider
    returns web search results.

PlaceEntityResolver
    resolves/merges a real-world entity.

MapPresentation
    draws pins/cards.

Routing
    turns place coordinate into route.

WebBrowser
    renders selected websites.

StructuredWebExtractor
    reads public structured metadata from a page.

Do NOT make GeckoView responsible for search.
Do NOT make SearXNG responsible for routing.
Do NOT make raw HTML parsing responsible for geographic truth.

==============================================================================
39. PRODUCT PRINCIPLE
==============================================================================

The feature is successful when Roadstr can move naturally through this chain:

    "I want something in the real world"
                  |
                  v
         Roadstr understands it
                  |
                  v
       finds trustworthy candidates
                  |
                  v
        shows them on the map
                  |
                  v
          lets me inspect them
                  |
                  v
        lets me interact with them
                  |
                  v
          takes me there

without turning Roadstr into:
- a Google Maps clone;
- a generic web browser;
- a centralized search service;
- an ad/tracking platform.

The objective is not "put a browser in Roadstr".

The objective is:

    MAKE THE OPEN WEB + OPEN GEOGRAPHIC DATA ACTIONABLE FROM THE MAP.

Preserve Roadstr's identity:
open-source, Android-native, privacy-conscious, Nostr-friendly, no Google
dependency, no hidden central backend, and navigation always remains the core reliable
function even when the discovery/web layer is unavailable.
